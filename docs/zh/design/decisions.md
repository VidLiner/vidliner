# VidLiner —— 架构决策记录（ADR）

[English](../../design/decisions.md)

状态：MVP（仅图片）里程碑已接受。
范围：本文记录系统**为什么**是现在这个样子。它完全从功能需求出发撰写。没有复制任何参考实现；只使用了通用软件架构思想（依赖图、端口与适配器、能力绑定、内容寻址存储），这些属于业界通行做法。

---

## 背景

面向对象视觉的训练数据增强不是"图像编辑"问题。交付物是
`图像 + 正确标注 + 溯源 + 质量证据`。一个返回了看似合理图片的生成模型，**不是**一个完成的数据点：变化过的对象必须重建标签空间，而未改动的部分必须仍然可被证明未改动。

因此 VidLiner 把增强当作**经校验的数据生产流水线**，而不是一次生成调用。

系统必须实现的流程：

```
输入数据集 → 样本分析 → 目标对象选择 → 分割/跟踪
→ 替换规划 → 候选生成 → 合成/精修
→ 质量评估 → 标注重建 → 验收门槛 → 数据集导出
```

---

## ADR-001 —— Clean-room 功能级重实现

**决策。** VidLiner 是独立项目。其包名、模块树、类名、配置格式、CLI、错误分类与文档，全部由功能需求独立推导而来。工作区中存在的两个参考代码库**仅**被用于研究*通用*架构思想，且在本仓库中不以任何形式存在：没有源代码、文件内容、标识符、DSL、命令体系、注释、文档、测试、manifest、品牌资源、目录结构或 LICENSE 文本。

**理由。** 需求是 clean-room 功能级重实现。把既有实现的衍生代码混入核心，会让溯源与许可变得含混，并引入与计算机视觉数据生产并不契合的设计约束。

**后果。**

* 本仓库中每个标识符都是为本项目选择的（见 `docs/zh/design/naming.md`）。
* 若某项能力只能靠复制获得，则从需求重新推导并重写；若暂时无法实现，则 `raise NotImplementedError`，而不是假装成功。
* 本仓库是独立 git 仓库，只有一段全新历史，没有任何 remote。

## ADR-002 —— 声明式 recipe 建立在带类型的 DAG 之上，而非命令式脚本

**决策。** 用户用 YAML recipe 描述*意图*（替换什么、保持什么、验收门槛多严、如何导出）。编译器把 recipe 与数据集探查结果一起转成显式的 `OperationGraph`。引擎执行这张图。

**理由。** 声明式 recipe 让三项需求同时成立：

1. **不花钱就能规划。** 图可以被构建和估算，而不调用任何付费模型（`vidliner plan`、`--dry-run`）。
2. **局部重跑。** 节点带身份与输入摘要，因此 QA 可以重跑、失败节点可以重试、中断的 job 可以恢复。
3. **绑定无关。** recipe 从不指名厂商，由运行时决定谁来满足能力。

**被否决的方案。**

* *以命令式脚本（Python API）为主接口。* 不可探查、不可恢复、没有天然的规划步骤、无法估算成本。Python API 仍然存在，但它是同一张图之上的次要接口。
* *依赖工作流引擎（Airflow/Prefect/Dagster）。* 运维过重，而且它们的执行单元是 task，不是"带类型的产物端口"。我们需要边级别的产物类型与内容哈希缓存。

## ADR-003 —— 用 Capability + Binding 取代写死模型

**决策。** Operator 声明它需要的*能力*（例如 `vision.object_detection.v1`）。Runtime Profile 决定由哪个具体 backend 提供该能力。Operator 从不导入或指名 backend。

**理由。** 同一份 recipe 必须能在只有本地模型的笔记本、有本地推理服务的机器、以及对接云端生成服务三种场景下运行而不需修改。这也是让 MVP 能用 fake backend 在无付费 API 下端到端测试的原因。

**后果。**

* Core（domain、core、pipeline、operators、quality）**零厂商导入**，由架构测试强制。
* 新增模型 = 新增一个 backend 包，而不是改流水线。

## ADR-004 —— backend 是唯一允许出现厂商 SDK 的地方

**决策。** 每个 backend 要么位于 `vidliner/backends/`（内置），要么位于 runtime profile 中点名的可导入插件模块。厂商 SDK 导入被限制在那里。有测试断言 `backends/` 之外没有任何模块导入厂商 SDK。

**理由。** 保持核心依赖倒置、可独立测试，并让"我们依赖了哪些供应商"这个问题可以只读一个目录就回答。

**后果。** `vidliner/backends/imageops.py` 是唯一被允许在其他层引用的模块——它是 mask/图像工具，不含任何厂商代码，且测试明确列出了这个例外。

## ADR-005 —— 内容寻址产物，以及按 `(operator, version, inputs, config)` 缓存

**决策。** 每个产物写入 `artifacts/<sha256[:2]>/<sha256>.<ext>`，并以摘要引用。节点缓存键为
`H(operator 名, operator 版本, 排序后的输入摘要, 规范化 config, 实现身份, 种子策略)`。缓存命中时，只有在文件仍然存在且哈希仍与记录一致的情况下才复用。

**理由。** 可复现性与可恢复性都可以归结为"我能否证明这些输入产出这个输出"。摘要身份还让溯源成为一次跳转而不是一行日志。读取时校验字节，可防止损坏缓存悄悄污染训练集。

**后果。** 重跑完全相同的 recipe 几乎免费；改一个阈值重跑会复用它上游的一切。

## ADR-006 —— 质量是一等阶段，且是硬门槛而非一个分数

**决策。** 验收由一组相互独立的指标门槛决定。指标可以是*警告*或*硬性*。硬性门槛失败即拒绝，与总分无关。QualityReport 为每个指标记录测量值、阈值与它贡献的 reason code。

**理由。** 单一加权分会让一次很好的分割掩盖一个被改坏的背景。对训练数据而言，真正致命的是那个会污染标签或教给模型错误背景不变性的失败。

**后果。**

* 拒绝是正常且预期内的结果，记录为 `QualityReject`——它是**样本**层面的结论，永远不是**系统**错误（见 ADR-010）。
* 门槛集合是数据，因此 `vidliner qa <job>` 可以在新策略下重新评估已有候选，而不重新生成任何东西。

## ADR-007 —— 标注必须重建，绝不盲目继承

**决策。** 替换之后，目标对象的标注通过在其生成图上重新执行检测/分割来重算。未改对象的标注会被继承，但需通过"背景差异证据"的保留校验。所有标注数据流经同一套内部 IR；COCO 与 YOLO 都是该 IR 的导入/导出器。

**理由。** 需求第一优先级是标注正确性。当对象形状或类别已变时，从源图沿用下来的框**在构造上就是错的**。把 IR 作为枢纽，让格式支持成为增量工作，也让往返测试成为可能。

## ADR-008 —— 感知 split 的 lineage 与去重属于流水线，而非事后插件

**决策。** 每个样本都携带 `split` 与 `lineage`（根源摘要 + 祖先）。只允许对 recipe 白名单内的 split 做增强（默认 `train`）。导出器校验没有任何增强后代与其源落到不同 split，并计算感知哈希，以同时拒绝相对于源集和已通过输出的近重复。

**理由。** 数据集泄漏与近重复泛滥是让增强流水线**有害**的两种失效模式。如果不在数据模型里从 ingest 起就记录 lineage，事后无法发现。因此数据模型必须自带。

## ADR-009 —— 用种子树取代环境随机性

**决策。** Job 有根种子。每个节点用稳定哈希按身份路径
`job_seed → sample_seed → target_seed → candidate_seed` 派生自己的种子。Backend 收到显式种子。没有任何模块调用模块级 `random` 或全局 `numpy.random` 状态。

**理由。** 可复现性是第三优先级，而环境随机性会让生成结果无法从 manifest 恢复。派生种子树还意味着：新增一个候选不会改变已有候选的种子。

## ADR-010 —— 系统失败与样本不合格是两码事

**决策。** 异常分类区分 `OperatorFailure`、`BackendFailure`、`ValidationFailure`、`QualityReject`、`InfrastructureFailure` 与 `Cancellation`。`QualityReject` 永不使 job 失败；它产出 `REJECTED` 候选与诊断。Job 汇总把 processed/accepted/rejected/review/failed 分开计数。

**理由。** 否则一条只产出 5% 可用数据的流水线会显得"成功"，而一次网关超时看起来像"数据不好"。

---

## ADR-011 —— 异步执行，核心逻辑不用线程

**决策。** 引擎基于 `asyncio`。Backend 以异步优先；包装阻塞 CPU 工作的 backend 声明其阻塞性，由引擎通过 `asyncio.to_thread` 派发。并发按 backend 设界，而不是全进程一个上界。

**理由。** 外部生成 backend 受延迟约束，并发有益；本地 GPU 工作必须串行。单个异步引擎加"声明式容量"同时处理两者，且不需要 MVP 并不需要的 worker/集群设计（见 ADR-014）。

---

## ADR-012 —— 状态用 SQLite，大块数据用文件系统

**决策。** Job、节点、候选与缓存状态放在单个 `state.db`（SQLite，WAL）。图像、mask 与报告放在文件系统，内容寻址。给人看的报告（HTML 复核、数据集报告）写成文件并在数据库中登记。

**理由。** 状态必须能跨重启存活且可查询（`vidliner jobs`、resume）。大块像素不属于数据库。对单机编排而言 SQLite 足够。

---

## ADR-013 —— 凭据绝不进入 recipe、manifest 或 git

**决策。** Backend 以*引用*方式获取凭据（`env:NAME`、`file:/path`，或 `value:` 明文——后者在仓库边界内的 recipe 中会被拒绝）。Manifest 记录用了哪个引用，绝不记录解析出的值。所有结构化日志与每个序列化 manifest 都过一遍脱敏过滤器。

**理由。** 溯源文件会随数据集一起分发；在那里泄漏一个 key 是不可挽回的。一个包含密钥的数据集仓库无法分发。

---

## ADR-014 —— MVP 是单机、仅图片、可用 fake backend 测试；模型为视频留出空间

**决策。** MVP 不实现分布式 worker、队列、云存储、Web UI 或视频替换。但领域模型已经包含 `ObjectTrack`、`FrameRef`、时序质量指标，以及能表达时序门槛的 `AcceptancePolicy`，引擎也已支持按 `(sample, target, candidate)` 阶段扇出。

**理由。** 需求是"API 与数据模型要为视频扩展留出空间，但不要过度设计 MVP"。具体而言：*接口*为时序做好准备，而 MVP 的 *operator* 仅支持图片，遇到视频输入抛 `NotImplementedError` 或明确的能力错误。

## ADR-015 —— 明确失败优于伪造成功

**决策。** 未实现的行为抛 `NotImplementedError`。不存在占位返回、没有 `pass` 函数体的 operator、没有 catch-and-continue。

**理由。** 一个组件可以静默 no-op 的流水线，会产出一个"看起来完整、其实不是"的数据集。既然产品承诺是"经过验证的训练数据"，静默 no-op 就是最危险的 bug。

---

## ADR-016 —— 每个节点都有确定性身份

**决策。** 节点 ID 由 `(operator 名, lineage 键, 序号)` 派生，其中 lineage 键是被采样/对象/候选身份的稳定摘要。扇出按显式键，而非列表位置，因此插入一个候选不会给其他候选重新编号。

**理由。** 缓存命中、恢复，以及跨运行的溯源对比，都依赖节点身份在无关编辑下保持稳定。

---

## ADR-017 —— 由流水线自行测量的能力不进入 binding

**决策。** `quality.background_preservation.v1` 由流水线在 `vidliner/quality/metrics.py` 中直接测量，并在 `BUILTIN_CAPABILITIES` 中登记。它保留在能力词汇表里（recipe 的验收门槛引用它，数据集报告也以它为准），但 runtime profile **不得**绑定它，`vidliner backend check` 把它报告为 `builtin`。另有测试断言：profile 中的每个 binding 都必须指向真正声明了该能力的 backend。

**理由。** 它最初被绑到 `builtin_metrics`，而该 backend 从未声明这项能力——于是预检把一个健康 profile 报成"有未覆盖能力"。手工声明的"元数据能力"与真正由适配器提供的能力混在一起，会让两边的真相都变得不可信。

**后果。** 能力词汇表明确区分"由适配器提供"与"内置测量"；`backend check` 只把前者计入覆盖率；新增内置测量需同步登记到 `BUILTIN_CAPABILITIES`。

## ADR-018 —— 用"在生成图上重新检测对象"把流水线闭合

**决策。** 在精修与评估之间插入 `verify.redetect` 阶段：它在**生成图**上检测对象，把检测结果与"被替换的区域"匹配，再重新分割该检测，并由这个 mask 推导 bbox、polygon 与面积。评估、标注与导出都描述**重建后的对象**；交给生成器的那个 mask 只承担一项职责——界定"被授权发生改变的区域"，也就是 `background_preservation` 所排除的那块。

**理由。** 没有这个阶段，若干检查是同义反复的。`target_presence` 与 `geometry` 把输入 mask 与它自己比较，于是"完全忽略 mask 的生成器""把对象挪走的生成器""原图返回的生成器"都能拿满分；`annotation_consistency` 度量的 mask 是关于**请求**的陈述而不是关于结果的陈述，而导出的标签继承了这个 mask。在内置合成生成器上这看不出来；换成真实 backend，它就是"经过验证的数据集"与"看起来没问题的数据集"之间的差别。

**后果。**

* 导出的标签来自真实存在的像素。图像里没有的对象不可能被赋予标签。
* "没找到对象"是一种**结果**：operator 返回 `found=False` 与空 mask，质量阶段记录 `OBJECT_NOT_FOUND`，门槛据此拒绝该候选。没有任何节点失败；样本全部不可用的 job 依然是 `SUCCEEDED` 且 `accepted=0`。
* 重新检测找的是对象**原来**的类别，而不是替换类别。检测器的标签集是固定的，不包含 `sedan` 这类子类别；向它索要子类别会在替换成功时也一无所获。替换结果是否属于目标类别，是语义评估器的判断，因为那是一个关于外观的问题。
* 该阶段需要真实的检测与分割 backend。内置启发式那一对足够跑 demo 和测试，但不足以为生产数据背书——这正是"默认 profile 仅限 demo"这条限制是必需而非装饰的原因。
* `annotate` 在对象缺失时输出一个结构合法、标记为 `not_found` 的**空** bundle，从而让"样本不合格"不会以节点失败的形式出现在 job 的失败计数里。样本不可用不等于 job 损坏，这正是 ADR-010 划出的界线。
